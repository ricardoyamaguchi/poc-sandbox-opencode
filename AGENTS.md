# AGENTS.md

iOS SwiftUI app (`PocSandbox`) using CocoaPods. No tests, CI, lint, or formatter config exist.

## Architecture — MVVM-C
- Every screen/feature must use **MVVM-C**: Model-View-ViewModel plus a Coordinator.
- Views stay declarative; ViewModels own state and business logic; Coordinators own navigation/routing.
- Each feature lives under `PocSandbox/Features/<Feature>/` with its View, ViewModel, and Coordinator. Shared code lives under `PocSandbox/Core/`; app-level routing lives under `PocSandbox/App/`.
- When touching an existing screen that still has logic in the view, move it to a ViewModel/Coordinator as part of the change.

## Documentation — update README before every push
- Every change must update `README.md` before pushing: new screens/flows, commands, scripts, dependencies, configuration, or behavior.
- Never push when the README does not reflect the change.

## Generated project — do not hand-edit
- `PocSandbox.xcodeproj` is generated by **xcodegen** from `project.yml`. Never edit it directly; edit `project.yml` and regenerate.
- Always open/build the **workspace** `PocSandbox.xcworkspace` (CocoaPods), never `PocSandbox.xcodeproj`.
- After changing `project.yml`, `Podfile`, or adding/removing source files: `make generate` (runs `xcodegen generate && pod install`).
- Source files under `PocSandbox/` are picked up automatically (xcodegen `sources: PocSandbox`), so new `.swift` files need no project edits.

## Makefile
- `make help` — lists targets; prefer `make` over raw commands.
- `make generate` — regenerates `PocSandbox.xcodeproj` and runs `pod install`.
- `make debug` / `make release` — build the workspace in that configuration.
- `make build` — build with current `CONFIGURATION` (default `Debug`).
- `make run` — build, boot the simulator, install and launch.
- `make clean` / `make distclean` — remove local build output / all generated files.
- Override variables: `make run SIMULATOR_NAME="iPhone 17 Pro" BUNDLE_ID=...`.

## Scripts
- `./scripts/generate.sh` — regenerates `PocSandbox.xcodeproj` and runs `pod install`.
- `./scripts/build.sh` — builds the workspace (override `SIMULATOR_NAME`, `CONFIGURATION`).
- `./scripts/run.sh` — builds, boots the simulator, installs and launches the app.

## Build
```
make build
```
- Equivalent raw command: `xcodebuild -workspace PocSandbox.xcworkspace -scheme PocSandbox -destination 'platform=iOS Simulator,name=iPhone 17' build`.
- Must specify a destination; the default fails on this machine.
- Only scheme to build is `PocSandbox` (other schemes are pod-generated).

## Toolchain quirks
- Xcode 26.3 SDK is iOS 26.2; the app deployment target is iOS 17.0 (`project.yml`).
- The installed simulator runtime is iOS 26.3 (`iPhone 17`, `iPhone Air`). Older runtimes (17.x/18.x) are present but not matched by default.
- If `xcodebuild` reports `iOS <ver> is not installed` or "Supported platforms ... is empty", the iOS platform component is missing: run `xcodebuild -downloadPlatform iOS` (large download).

## Dependencies
- Managed by CocoaPods via `Podfile` (currently Alamofire). Pin versions there; `Podfile.lock` is checked in.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. When the answer is under a Markdown heading, `graphify section "<heading>"` prints that section's text, so the .md need not be opened. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
